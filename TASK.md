## 2. Описание

Разработайте консольную мини-игру в духе 2048 на поле 4×4. На поле появляются плитки со
значениями кэшбэка, а две одинаковые плитки объединяются в следующую:

```text
1% + 1% = 2%    2% + 2% = 4%    ...    16% + 16% = 32%
```

У игрока ограниченное число валидных ходов. Его цель - получить максимальную плитку и набрать
как можно больше очков.

У проекта есть второй, продуктовый слой. Итоговая плитка определяет награду игрока, а дорогую
награду должна получать ограниченная доля участников кампании. Например, в batch-симуляции
максимальную награду могут получить не более 20% игроков.

Промо-игры и кэшбэк-механики стоят компании реальных денег. Перед запуском кампании необходимо
оценить, какая доля пользователей доберется до каждого уровня награды. В этом проекте вы пройдете
весь цикл:

1. Игровой движок.
2. Конфигурируемая кампания.
3. Симуляция на тысячах игроков.
4. Отчет со статусом `OK` или `FAILED`.

Задание тренирует:

- чистую детерминированную логику слияния блоков
- отделение бизнес-правил от случайности и консольного интерфейса
- конфигурацию поведения без захардкоженных параметров кампании
- точную работу с процентами и вероятностями
- инварианты и явные ошибки конфигурации
- воспроизводимые симуляции и сбор статистики

## 3. Требования к реализации

Точка входа CLI находится в `cmd/cashback-merge/main.go`. Остальную структуру решения определите
самостоятельно. Остальная структура решения не задается. Если точка входа или команды меняются, обновите
Makefile и GitLab CI.

Конфигурация кампании загружается из JSON-файла. Обязательные параметры:

```json
{
  "movesLimit": 100,
  "spawnRules": [
    {"cashback": "1", "probability": "0.85"},
    {"cashback": "2", "probability": "0.15"}
  ],
  "maxRewardCashback": "32",
  "maxRewardAllowedRate": "0.20"
}
```

Добавьте в конфигурацию таблицу наград. Ее JSON-структуру выберите самостоятельно и опишите в
README. По максимальной плитке должно быть возможно однозначно определить уровень награды.

Обязательные свойства решения:

- размер поля в базовом задании всегда равен 4 на 4
- начальное поле содержит две плитки в разных клетках
- координаты находятся в границах поля, в одной клетке находится не более одной плитки
- `movesLimit > 0`, spawn-правила не пусты, а их вероятности в сумме точно дают 1
- значения кэшбэка и вероятности не хранятся в `float`
- одинаковые конфигурация, seed и стратегия дают одинаковые состояние и отчет
- некорректная конфигурация отклоняется до начала игры или симуляции
- игровая логика отделена от загрузки файлов и консольного ввода-вывода

Для точной арифметики храните кэшбэк целым числом, а вероятности - целыми в выбранном масштабе
или как `big.Rat`. Не преобразуйте JSON-значения вероятностей через `float64`.

## 4. Merge request

При создании MR выберите шаблон [`requirements`](.gitlab/merge_request_templates/requirements.md).
В нем уже находится чек-лист для проверки работы.

### MR1 - модель, конфигурация и начальное состояние

Реализуйте:

- поле 4×4 и модель плитки с уровнем кэшбэка
- состояние игры: поле, лимит и число использованных ходов, score и признак завершения
- загрузку конфигурации кампании из JSON-файла
- валидацию всех обязательных параметров и таблицы наград
- создание начального состояния с двумя плитками по заданному seed
- текстовое представление поля

Проверяйте как минимум следующие ошибки: пустые spawn-правила, вероятность вне допустимого
диапазона, сумма вероятностей не равна 1, неположительный `movesLimit`, некорректный cashback и
неполная таблица наград.

### MR2 - движок ходов

Реализуйте `apply_move(state, move)` для направлений `UP`, `DOWN`, `LEFT`, `RIGHT`.

Правила сдвига влево для одной строки:

```text
[1, 1, empty, empty] -> LEFT -> [2, empty, empty, empty]
[1, 1, 1, empty]     -> LEFT -> [2, 1, empty, empty]
[1, 1, 1, 1]         -> LEFT -> [2, 2, empty, empty]
[2, 2, 4, 4]         -> LEFT -> [4, 8, empty, empty]
```

Ключевые правила:

- сначала все плитки сдвигаются к выбранному краю, затем соседние равные плитки объединяются
- одна исходная плитка не объединяется дважды за ход:
  `[1, 1, 2, empty]` превращается в `[2, 2, empty, empty]`, а не в `[4, empty, empty, empty]`
- ход считается невалидным, если после сдвига и слияния поле не изменилось
- невалидный ход не меняет состояние, не расходует лимит и не создает плитку
- после каждого валидного хода появляется ровно одна новая плитка в свободной клетке
- score увеличивается на сумму значений плиток, созданных объединениями в этом ходу:
  `[2, 2, 4, 4] -> LEFT -> [4, 8, 0, 0]` добавляет к score `4 + 8 = 12`
- игра не заканчивается при достижении 32% и продолжается до лимита ходов
- если на поле не осталось ни одного валидного хода, игра завершается досрочно
- логика появления новой клетки отделена от логики слияния

Выделите чистую детерминированную операцию сдвига и объединения. Случайное появление выполняется
отдельно и только после того, как ход признан валидным.

### MR3 - награды, симуляция и отчет

Добавьте:

- взвешанную случайность для выбора значения новой плитки по `spawnRules`
- определение итоговой награды по максимальной достигнутой плитке
- batch-симуляцию для заданного числа игроков
- стратегию `random`, равновероятно выбирающую одно из доступных направлений
- проверку ограничения на долю максимальной награды
- сохранение итогового отчета в файл

Если максимальная плитка не меньше `maxRewardCashback`, игрок получил максимальную награду.
Фактическая доля рассчитывается как отношение числа таких игроков к общему числу игроков:

```text
actualMaxRewardRate <= maxRewardAllowedRate -> OK
actualMaxRewardRate >  maxRewardAllowedRate -> FAILED
```

Это эмпирическая проверка для конкретных конфигурации, seed, количества игроков и стратегии, а не
математическая гарантия ограничения.

Пример запуска:

```bash
make run ARGS="simulate --config campaign.json --players 10000 --strategy random --seed 42 --output report.md"
```

Отчет в текстовом, JSON- или Markdown-формате должен содержать:

- число игроков и лимит ходов
- seed и название стратегии
- распределение максимальных плиток
- распределение наград
- средний и максимальный score
- число и долю игроков с максимальной наградой
- допустимую долю максимальной награды
- статус `OK` или `FAILED`

## 5. Тесты

Готовых тестов в шаблоне нет. Напишите тесты самостоятельно и проверьте:

- валидная конфигурация принимается
- пустые правила появления новых клеток, сумма вероятностей не равная 1 и `movesLimit <= 0` отклоняются
- начальное поле содержит две плитки в разных клетках
- одинаковые конфигурация и seed дают одинаковое начальное поле
- `[1, 1, 2, empty]` превращается в `[2, 2, empty, empty]` без двойного слияния
- ходы во всех четырех направлениях работают симметрично
- невалидный ход не меняет поле, score и счетчик ходов и не создает плитку
- после валидного хода появляется ровно одна новая плитка
- score увеличивается только на результат выполненных объединений
- после `movesLimit` валидных ходов игра завершается
- максимальная плитка 16% дает награду соответствующего уровня
- одинаковые конфигурация, seed и стратегия дают одинаковый отчет симуляции
- отчет содержит распределения, долю максимальной награды и статус `OK` / `FAILED`
- для сценариев по обе стороны лимита правильно выбираются статусы `OK` и `FAILED`

Не проверяйте взвешанный рандом нестабильным тестом "примерно 85% на небольшой случайной выборке".
Используйте фиксированный seed, управляемый источник случайности или проверку граничных интервалов.

Команда `make test` запускает стандартный `go test` и формирует:

- `coverage.out` с профилем покрытия
- `coverage.html` для просмотра в браузере

`make test-race` отдельно включает race detector. Для него локально нужен Go с поддержкой CGO и
C-компилятор.

## 6. Ограничения и советы

Ограничения:

- используйте стандартный текстовый ввод и вывод
- не добавляйте GUI, веб-интерфейс или сетевой сервис
- не подключайте базу данных, банковский API и настоящую выдачу кэшбэка
- не реализуйте сложный AI - для базового задания достаточно стратегии `random`
- не требуется математически доказывать ограничение на долю награды
- не используйте внешние библиотеки для правил игры и управления состоянием

Советы:

- начните с чистой функции обработки одной строки, затем примените ее ко всему полю
- не изменяйте исходное состояние, пока не установлено, что ход валиден
- отделите merge, spawn, стратегию, симуляцию и формирование отчета
- загружайте JSON через `encoding/json` и полностью валидируйте конфигурацию до запуска
- преобразуйте строковые вероятности в точное представление сразу после загрузки
- для `math/rand/v2` создавайте локальный генератор через `rand.New` и явно заданный source
- явно и воспроизводимо получайте seed каждой игровой сессии из общего seed симуляции
- сортируйте ключи перед выводом данных из `map`, чтобы отчет был воспроизводимым
- передавайте `io.Reader` и `io.Writer` консольному слою вместо прямого доступа к stdio
- не печатайте состояние каждой партии во время batch-симуляции
- запускайте `go test -race ./...` при изменении кода симуляции
- избегайте нестабильных статистических тестов
